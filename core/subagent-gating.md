# Subagent Gating（子代理啟用閘門）

> **狀態**：v0.1
> **位階**：core 通用條款（opt-in，governance overlay）。
> **依存**：`charter-config.md`（啟用與參數）；角色邊界交叉引用 `role-separation.md`、人工操作交叉引用 `human-gates.md`。
> **保證強度**：單 actor 自律；部署 guard 時，已列工具名的放行部分為結構強制（正則黑名單，非安全邊界）
> **檢測時點**：runtime

## 0. 啟用與位階

僅在 `enabled.subagent-gating: true` 時生效；缺值視為 false。預設不啟用子代理；允許數量與並行上限由 profile 決定，範例值見 [governance overlay](../tools/profiles/governance.overlay.yaml)。

## 1. 條文

| 面向 | 合規規定 |
|---|---|
| 預設與核准 | profile 的未核准子代理數為零。包含 Workflow 建立的子代理；開啟前告知用途、改檔／唯讀類別、並行規模與範圍，取得人工核准。 |
| 核准後上限 | 改檔與唯讀子代理各自遵守 profile 的同時上限，不以批次派發或角色更名增加名額。範例 profile 分別給改檔與唯讀上限；超限須另行核准。 |
| 不可遞迴 | 子代理不得再建立子代理；主導者須將此限制寫進工作包。核准只授權該工作包，不自動向下一層傳遞。 |
| 核准通道 | 核准須來自 AI 無法自行設定的通道；例如由人控制 CLI 啟動器、在啟動環境注入時效型變數。期限、變數名與工具名從 guard 設定讀取，不能由 AI 改設定、改環境或啟動替代行程自授權。 |
| 角色責任 | 子代理不改變角色互鎖、抽驗權或主導者責任；不得用子代理代行主導者無權執行的工作。 |

## 2. 設計動機

並行是資源與責任的擴張，需要先定規模。零預設與禁止遞迴避免隱性派工；核准與工具放行分層，避免把「hook 沒擋」當作「人同意」。

## 3. 授權的保證邊界

在 shell 工具內改變環境通常不能回寫既有父 CLI；但 `VAR=… <cli>` 開出的子行程會繼承該環境，不能因此宣稱「AI 無法設置任何 CLI 的授權」。若 AI 可啟動替代 CLI、改 guard／配置，環境變數本身不是不可偽造的人工核准證據。採用方應將啟動器與核准狀態放在 AI 無寫入權的控制面；做不到時明示仍屬自律。

[PreToolUse guard](../tools/pretooluse-guard-spec.md) 範例只檢查工具名與時效，不計並行數，也不驗遞迴血緣；數量與禁止遞迴仍須主導者遵守與抽驗。

## 4. 反例

- ❌ 主導者自行設授權變數再開 CLI，宣稱取得人工核准。
- ❌ 唯讀代理為方便再派出改檔代理。
- ✅ 人核准規模後由受控啟動器放行，主導者追蹤並行數與角色邊界。
